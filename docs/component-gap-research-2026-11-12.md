# ZUI 组件缺口与设计建议

检索日期：2026-11-12。基于当前 Registry、公共导出、组件源码、业务区块、Builder、内容协作工作台与 RFC，并查看外部官方产品文档。本次为需求和设计研究，未新增组件实现，也未重跑项目测试。

后续实施补充：文档工作台已接入 [Word、Excel、PDF 页面内完整编辑器](office-full-editor.md)，并将原生画布提炼为公共 `OfficeEditor` 组件，当前源码组件数增至 72，尚未发布。下述计数保留研究时的 71 项快照。专业文档编辑由独立部署的 ONLYOFFICE 提供，通用文件协作 API 与应用级远端共享仍属于待提炼能力。

## 结论

当前已有 **71 个正式组件、16 个业务区块**，分别由 `registry/registry.json` 实际条目与组件目录复核。基础表单、浮层、导航、日期与反馈覆盖已经完整。下一轮最有价值的方向是：让用户更快找到数据、更可靠地导入数据，以及更清楚地控制 AI 工作过程。

建议先做 **FilterBar / SavedViews、ImportWizard、AIComposer / ToolTrace** 三组。DataGrid 同属高优先级，但工程量明显更大，应沿现有 RFC 分期推进。版本对比、看板、预约和文件协作已有探索，重点是补齐通用接口与真实业务状态。

下表中的“创新”指相对当前 ZUI 增加新的任务能力与交互组合，不主张这些概念为行业首创。“好看”是建议的设计方向，需在后续原型中验证。

## 首批三组的具体设计

### 1. FilterBar + SavedViews

消费场景：商品/订单管理，以及任务看板。两者共享条件模型，但自行决定如何请求和呈现数据。

推荐首屏结构：`[视图：我的待办 ▾] [状态：进行中 ×] [负责人：我 ×] [+ 添加条件] [保存视图]`。复杂 AND/OR 条件进入弹层，常用条件留在页面工具栏。

首版提供文本、枚举、数字、日期字段；受控条件、增删清空、明确应用/重置；保存和恢复筛选及排序。保存接口由应用提供，组件不直接绑定浏览器存储。视图名称与实际条件同步，修改后显示“未保存”。列显示和重排留待 DataGrid 对应能力成立后接入。

可选创新探索：一句话描述转成**待确认的条件标签**。例如“最近七天的异常订单”先展示日期与状态两项条件，确认后再执行；规则转换可先用确定性解析或外部回调，不把模型请求塞进基础包。

### 2. ImportWizard

消费场景：客户名录导入，以及商品基础数据导入。

流程为 `选择文件 → 匹配字段 → 校验修正 → 确认提交`。匹配页以“文件列名 / 目标字段 / 数据样例”排列；校验页显示错误行数与当前问题，点击问题定位相应单元格。修正后即时重新校验。

首版只支持 UTF-8 CSV 或调用方已解析的行数据，并提供解析、校验和提交适配接口。列名别名匹配属于建议，需允许用户确认与覆盖。支持必填、枚举、格式校验；错误行定位、修改；处理重复提交、部分成功与失败保留。Excel 解析和大文件 Worker 作为后续可选适配。

创新重点：导入前完成数据修复；提供“修正预览”与明确应用动作，避免自动改动原始值而用户无从判断。

### 3. AIComposer + ToolTrace

消费场景：文档辅助修改，以及订单/任务分析助手。

输入区从上到下为附件/记录标签、多行文本、操作栏；执行区显示具名任务条目，例如“读取 3 份资料”“生成修改建议”，并能展开输入摘要与结果。来源与回答关联，不把全部执行日志常驻在消息正文里。

首版输入为受控文本、附件、上下文标签；明确 idle/submitting/running/error 状态；发送、停止、失败重试回调；发送方式可配置并处理中文 IME。执行条目区分等待、运行、成功、失败、取消；需要用户确认的业务动作提供确认插槽。

AIComposer 优先复用 Input.Textarea、Upload、Tag、DropdownMenu、Button。ToolTrace 复用 Collapse、Steps、Progress 等组织公开执行事件，不依赖模型提供内部思维文本。网络、模型、会话持久化与业务执行由应用端负责。若两个消费场景显示组合即可满足需求，可以先以区块发布，再提炼稳定公共组件。

## 其余原型如何推进

- **ActivityInbox**：有通知流与持久已读状态的真实消费方后，可以优先正式化为区块；它解决消息中心任务，现有 Notification 继续负责临时反馈。
- **FilePreview / ContentEditor / CommentThread**：沿 RFC-006 提炼公共接口，复用已完成的本地工作台；远端调用与权限作为适配契约。
- **MetricBoard**：扩展 Statistic 或仪表盘区块，增加可信的趋势对比、异常解释和明细入口；无需新建通用图表引擎。
- **AccessControl / ApprovalFlow**：保留业务区块定位，先接真实人员、资源和流程定义；前端展示不能替代应用端授权或审批状态判定。
- **StyleConfigurator**：深化令牌预览、对比度检查和导出，作为设计工具；不需要成为基础 UI 控件。

## 视觉与体验要求

以 ZUI 现有语义令牌为基线：中性画布、细边框、清楚的标题与留白，主色用于当前选择和主要动作。状态同时使用文字/图标，数字采用统一对齐；避免用多种强调色争夺注意。

每项至少设计默认、空态、加载、失败与完成画面。紧凑和舒适密度应兼顾触控目标；320px 下条件标签换行、向导纵向排列、复杂画布提供可用的列表路径。动画只解释位置或状态变化，并响应 reduced-motion。明暗主题、键盘焦点和实际业务数据下的长文本，均纳入原型验收。

## 实施顺序与首版约束

1. **先验证 FilterBar / SavedViews**：复用两个列表页面，最快验证高频价值。
2. **落地 ImportWizard 区块**：补齐独立的业务数据进入流程；首版无需等待 DataGrid。
3. **验证 AIComposer / ToolTrace 区块**：以真实公开事件展示工作过程，先明确回调与状态契约。
4. **沿 RFC 推进 DataGrid**：首版保持排序、筛选、选择、列宽、固定列与键盘导航范围；单元格编辑、重排与聚合后续评估。
5. **深化协作、看板、流程与排期**：按真实消费需求决定是否独立组件化。

不优先补 Carousel、重复的 Textarea/Password/Search、独立图表引擎或完整富文本引擎。ContextMenu 可先扩展既有 DropdownMenu；OTPInput 等较小表单控件可在存在验证场景后补齐。视觉创新应来自清晰、完整的新任务路径，而不是增加无业务作用的装饰控件。
